# Security Hardening Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Address the security review findings before pushing the final deployment workflow.

**Architecture:** Terraform generates the Rails `SECRET_KEY_BASE` instead of accepting a predictable placeholder default. The EC2 deploy script avoids shell tracing, and the GitHub Actions deploy step avoids printing full SSM stdout/stderr where app errors could include sensitive environment values.

**Tech Stack:** Terraform, AWS Secrets Manager, random provider, EC2 user-data, GitHub Actions, SSM.

---

### Task 1: Remove Predictable Rails Secret

- [x] **Step 1: Remove placeholder variable**

Remove the default:

```text
replace-me-before-running-the-real-rails-app
```

- [x] **Step 2: Generate the secret in Terraform**

Use a generated 128-character `random_password` value for `SECRET_KEY_BASE` in the app runtime secret.

- [x] **Step 3: Avoid exporting secret-derived outputs**

Keep validation inside Terraform tests instead of adding a module output derived from the secret value.

### Task 2: Reduce Secret Exposure In Deploy Logs

- [x] **Step 1: Disable shell tracing in deploy script**

Use:

```bash
set -euo pipefail
```

instead of:

```bash
set -euxo pipefail
```

- [x] **Step 2: Avoid full SSM output in GitHub Actions logs**

Query only:

```text
Status
ResponseCode
```

### Operator Note

After `terraform apply`, Terraform writes a new Secrets Manager version with the generated `SECRET_KEY_BASE`. Redeploy or restart the Rails container so it reads the rotated value. Existing signed Rails cookies and sessions may be invalidated.
